# 架构

官方原文：harness `docs/architecture.zh.md`（改动 packages/ 之前必读）。本文假定你已了解 Cordis（见 [Cordis入门](Cordis入门.md)）。

## Cordis

Cordis 是 dsh 底层的框架：插件向共享上下文贡献服务、类型化事件和可逆副作用。产品的每一部分都是插件（模型适配器、工具注册表、会话日志、agent loop 本身），因此每一部分都可以从配置替换。**不存在需要打补丁的特权内核**：扩展 dsh 的方式是把插件挂载到其他插件旁边，各项注册都是副作用，随插件卸载撤销。

## Profile 与组合包

运行中的 `dsh` 是一棵插件树，由启动时按序叠加的各层组合而成：

- **profile**：Harness home 中的具名组装（`$DSH_HOME/profiles/<name>`），列出自己叠放的组合包、存放树外插件、保存用户自己的 cordis.patch.yml。`web` 和 `headless` 随发行版交付。
- **组合包**：Cordis 配置项及其挂载代码的分发格式；它插入的内容始终可被其上各层 patch。

两者都在各自 package.json 的 `dsh` 字段声明自己：`dsh.profile` 列组合包，`dsh.bundle` 指向 patch 文件。`dsh-base` 是每个 profile 的第一层（模型适配器、工具、持久化、沙箱与审批、设置、凭据、遥测）；`dsh-web-app` 增加浏览器应用；`dsh-headless` 增加一次性运行器且完全不带服务器。

层顺序：各 bundle patch（按 profile 列表顺序）→ profile 的 cordis.patch.yml → home 级 → `--patch` overlay。patch 按 id 定位条目并替换其**整个** config，或插入新条目。查看实际配置树：`dsh --profile web --dump-config`（打印出的任何条目都可以被你的 patch 替换）。

## 核心包

| 包 | 职责 | ctx 键 |
| --- | --- | --- |
| core/session | 仅追加的 SessionEvent 日志和内存存储 | `ctx.sessions` |
| core/system-prompt | 提示词片段与工具 schema 的组装 | `ctx.systemPrompt` |
| core/tools | 作用域化工具注册表和带把关的执行流水线 | `ctx.tools` |
| core/agent | Agent 接口、活跃 agent 注册表和 `agent/*` 事件 | `ctx.agents` |
| core/agent-loop | 实现该接口的默认驱动器 | `ctx.agentLoop` |
| core/scope | 按 agent 划分作用域的注册原语 | 库，无 ctx 键 |
| llm/llm | 消息与流式词汇表，以及适配器 seam | `ctx.llm` |

## 事件三域（选对事件域是大多数改动的第一个决定）

- **会话事件**（`session/event` 广播）：追加到日志的持久事实。事实必须在重新加载后仍存在时使用。
- **Agent 事件**（`agent/*`）：携带活跃 Agent——inbox、步骤、状态、请求、验证、续跑。观察或拦截进行中的工作时使用。
- **能力事件**：无需导入循环即可向某个 seam 附加策略与适配器（`fs/*`、`tools/*`、`telemetry/*`）。

## 轮次流程

一个**步骤** = 一次模型请求 + 它调用的工具。一个**轮次**包含零个或多个步骤：领取首条输入之前打开，不再欠任何工作时关闭。

```text
turn/start
  领取 next-step 输入 + 一条排队消息
  组装提示词片段 + 工具 schema
  -> agent/pre-step                   reject | enter(messages)
     reject / 首次 enter 改写为空 -> 无步骤关闭轮次
     step/start
     进入的消息追加为 user/message
     从日志派生模型历史
     agent/request -> llm/stream -> assistant/chunk* -> assistant/message
     tool/call* -> tools/pre-execute -> tools/execute -> tools/post-execute -> tool/result*
     step/end
     工具欠另一次请求 / next-step 输入到达 -> 领取 -> 下一步骤
  -> agent/turn-stopping
turn/end
```

- `turn/*`、`step/*`、`user/message`、`assistant/*`、`tool/*` 是持久会话事件；其余是三个事件域的实时扩展点。
- `agent/pre-step`、`agent/request`、`llm/stream`、三个 `tools/*` 是 waterfall（监听器必须调 `next()` 委托）；`agent/turn-stopping` 是 serial（没有 `next()`）。
- 输入经同一个 inbox 到达驱动器；注入的上下文留在 inbox 中，直到另一条消息唤醒它。
- `agent/pre-step` 决定模型看到什么：可改写已领取的消息或直接拒绝。

## 会话日志

会话日志是模型所见上下文的来源：`deriveMessages()` 从中投影模型历史；原始 `assistant/chunk` 保证回放与 UI 保真。fork、恢复、transcript、遥测、持久化都派生自该事件流。**模型可见即已记录**——抵达模型请求的一切都必须能从日志重建（运行时不变量）。因此新增一项模型可见输入就需要新增一个会话事件：扩展 `SessionEventMap` 并从日志渲染。

## 能力 seam

一个 **seam** 是一项可替换能力，含三种角色：Service Definition / Service Provider / Consumer（通常是面向模型的工具）。单一角色不是 seam；添加能力意味着把三者一并设计。seam 正是「替换一个提供方就改变整个产品」的原因：文件系统与进程提供方共享同一执行世界，把它们指向远程沙箱，Bash、PTY、LSP 一并搬过去。

## 新行为的归属位置

| 目标 | 机制 |
| --- | --- |
| 添加模型提供方 | 在 `ctx.llm` 注册适配器 |
| 添加面向模型的能力 | 在 `ctx.tools` 注册；schema 加入提示词组装 |
| 让某会话拥有不同能力集合 | 组装 agent preset；服务行需 `isolate` realm |
| 添加 shell 执行 | 注册 `ctx.shell` 后端；本地后端经 `ctx.subprocess` spawn |
| 添加持久化终端执行 | 注册 `ctx.terminals` 后端 + dsh-tool-terminal |
| 添加用户命令 | 在 `ctx.commands` 注册；无需模型轮次即分派 |
| 添加后台工作 | 在 `ctx.jobs` 注册；`job_*` 工具收集/停止 |
| 添加文件系统访问或策略 | 注册 `ctx.fs` 提供方，或监听 `fs/*` 事件 |
| 限制所启动的进程 | 用 `ctx.sandbox` 后端；消费方启动前包装 argv |
| 拦截请求、工具或轮次 | 用相应 `agent/*` 或 `tools/*` 事件；`agent/turn-stopping` 停止轮次 |
| 添加模型可见上下文 | 调用 `agent.inject()`；落到下一次获准请求 |
| 添加 UI 或编辑器集成 | 驱动 `ctx.agents` 并从 `session/event` 渲染 |
| 添加 Web Client Chat 节点 | 注册 ConversationNodeDefinition + keyed renderer |
| 添加持久会话状态 | 扩展 `SessionEventMap`；从日志渲染和回放 |
| fork 活跃会话 | `ctx.sessions.fork(source, boundary?, childSessionId?)` |
| 将注册项限定到单个 agent | 用该 agent 的 `agent.ctx` |

对应关系速查：轮次时序见 [Agent生命周期](Agent生命周期.md)，工具把关见 [Tool执行](Tool执行.md)，服务清单见 [能力服务](能力服务.md)。

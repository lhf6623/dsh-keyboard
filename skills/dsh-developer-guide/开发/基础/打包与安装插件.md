# 打包与安装插件

官方原文：harness `docs/user/develop/basic/publish.zh.md`。

## 两个概念，两种 manifest

都由一份 package.json 描述，但 `dsh` 键下携带的 manifest 种类不同，回答的问题也不同：

- **组合包（bundle）**——附带一个配置层的 npm 包，声明 `dsh.bundle`，回答「这个包贡献什么」：一个插入/覆盖插件行的 patch 文件。**这是你编写并分发的东西。**
- **profile**——`$DSH_HOME/profiles/<name>` 下描述一份可启动组合的目录，声明 `dsh.profile`，回答「这套配置由哪些组合包按什么顺序组成」。这是用户用 `dsh --profile <name>` 启动的东西。

没有东西同时是两者；没有 `dsh.bundle` 声明的包装上后只是普通依赖（有一次性警告，不激活任何层）。

## 组合包 manifest

```json
{
  "name": "dsh-hello-plugin",
  "version": "0.1.0",
  "type": "module",
  "main": "index.js",
  "files": ["index.js", "cordis.patch.yml"],
  "dsh": { "bundle": { "patch": "./cordis.patch.yml" } }
}
```

```yaml
# cordis.patch.yml——插件行按包名引用（不是相对源码路径），Node 才能解析到已安装代码
- insert:
    - id: hello
      name: dsh-hello-plugin
```

## 安装进 profile

`dsh plugin --profile <name> <args...>` 在 profile 目录内转发给 pnpm（add/remove/why/update 全可用），并自动维护 `dsh.profile.bundles` 有序列表：

```sh
dsh plugin --profile demo add ./hello-plugin        # 本地 checkout / tarball
dsh plugin --profile demo add github:you/hello-plugin  # git 安装
dsh plugin --profile demo remove dsh-hello-plugin
dsh --profile demo --dump-config                    # 启动前验证 patch 层
dsh --profile demo
```

## 加载顺序与 patch 规则

生效配置在空根之上逐层组合（**后者按行胜出**）：

1. profile 的 `dsh.profile.bundles` 列表所列的各个组合包 patch，按列表顺序；
2. profile 自己的 `cordis.patch.yml`；
3. home 级 `$DSH_HOME/cordis.patch.yml`（各 profile 共享的机器本地偏好）；
4. 每个 `--patch <path>` overlay，按 argv 顺序。

两条推论：

- **patch 按行整体替换** `config` 值，不深合并：覆盖别人的行必须重述该行全部键；你的行也要给用户大概率会保留的默认值（用户可在自己 profile 覆盖你，不必改你的包）。
- 行没有显式 `id` 时每次读取都生成新 id → 任何配置编辑都会把该行当「删除+重加」重挂载。**行要带 `id`。**

## Git 安装的构建脚本这道坎

`dsh plugin add github:you/hello-plugin` 拉的是**源码，不跑 build 脚本**——TypeScript 包到手没有 lib/ 输出，加载会失败。三种交付方案：

1. **提交构建产物**（dsh-vibe 的做法）：把 lib/ 提交进仓库，零授权零摩擦，安装即用。
2. **`prepare` 脚本 + allowBuilds 授权**：`prepare` 在 pnpm git 安装后自动运行，必须自包含（不能假设旁边有 monorepo）；pnpm ≥10 默认拒绝运行 git 依赖的 prepare，用户需按 dsh 提示把包键写进该 profile 的 pnpm-workspace.yaml。**授权 = 允许该包代码在安装时于用户机器上执行**，只对可信源授权并锁 commit。
3. **发布 npm**（`pnpm publish` 前构建好 lib/）或 **`pnpm pack` 交付 tarball**——均无需构建权限。

## 让表层组合包持有自己的命令行

定义了可运行应用的组合包挂载一个普通提供方插件：该插件 `inject = ['cmdlineArgs']`，用 `@deepseek-ai/dsh-cmdline` 的 `parseCmdline` 解析自己的 commander program。受参数配置的行注入该提供方服务并在自己的 `!!js` 选项里读取（如 `port: !!js ctx.myAppStartup.port ?? 8080`）。遇到 `--help` 时提供方不发布服务，这些行不会激活。

## dsh-vibe 实例

[package.json](../../../package.json) 的 `dsh.bundle` 指向 [cordis.patch.yml](../../../cordis.patch.yml)（宿主行 `id: vibe` + 默认 entry config）。发布四步：`npm run build` → `node --check lib/index.js && node --check lib/client.js` → bump version → 提交（含 lib/）→ `dsh plugin --profile web remove dsh-vibe` → `dsh plugin --profile web add github:<you>/<repo>`。发布包名 ≠ 仓库名是常态（dsh-vibe 的仓库名与包名就不同），别混。

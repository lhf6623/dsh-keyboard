# 插件配置

官方原文：harness `docs/user/develop/basic/config.zh.md`。

## 定义 Config：接口 + 同名 schema

导出 `Config` 接口和同名的 Schemastery schema（Cordis 接受任意 Standard Schema 验证器，**普通对象不行**）；默认值直接写在 schema 里：

```ts
import type { Context } from "@deepseek-ai/cordis";
import z from "@deepseek-ai/schemastery";

export const name = "my-plugin";

export interface Config {
  greeting: string;
  maxRetries: number;
  mode: "fast" | "accurate";
}

export const Config: z<Config> = z.object({
  greeting: z.string().default("Hello"),
  maxRetries: z.number().default(3),
  mode: z.union(["fast", "accurate"]).default("fast"),
});

export function apply(ctx: Context, config: Config) {
  // config 已校验并补全默认值
}
```

## 在 cordis.yml 里覆盖

```yaml
- id: hello
  name: "./src/my-plugin.ts"
  config:
    greeting: "Hi there"
    maxRetries: 5
```

- 配置不合法 → 插件加载失败（fiber FAILED），错误信息明确，绝不带病启动。
- **配置变更触发 HMR**：改 entry 的 `config` → 旧实例卸载（effect 全部回卷）→ 新配置重新 apply。
- `!!js` 标签：仅在 entry 的 `config` 与 `disabled` 字段内有效，加载时求值（如 `greeting: !!js process.env.X ?? 'Hello'`）；`disabled: !!js ...` 在每次挂载决策时求值，可做平台门控。

## 设计原则

- **无硬编码可调参数**：凡是不同部署可能取不同值的参数都必须是配置字段。检验标准：能否只改 cordis.yml 不改代码？
- **配置错误要响亮**：约束写在 schema 里，使无效配置在加载时就失败；对服务/已注册资源的引用用依赖注入（inject）解决。
- 配置通过 schema 但引用的资源不可用时，在能解析引用处立即拒绝。

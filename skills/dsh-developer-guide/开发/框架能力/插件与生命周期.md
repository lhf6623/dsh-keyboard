# 插件与生命周期

官方原文：harness `docs/user/develop/framework/index.zh.md`；动手版：`docs/cordis-tutorial/02-lifecycle-and-effects.zh.md`。

## Fiber 状态机

每个被加载的插件都拥有一个 Fiber 作用域：

```
PENDING → LOADING → ACTIVE
                 ↘ FAILED
ACTIVE → UNLOADING → DISPOSED
```

| 状态 | 含义 |
| --- | --- |
| PENDING | 已声明，但所需依赖未就绪 |
| LOADING | 依赖就绪，正在执行 `apply` |
| ACTIVE | 插件运行中 |
| FAILED | `apply` 抛出异常 |
| UNLOADING | 正在卸载并释放资源 |
| DISPOSED | 已完全卸载 |

**「插件没生效」第一诊断**：PENDING 是合法状态——某个 `inject` 的服务无人提供时插件静静等待，不报错、无输出。排查：遍历注册表找 PENDING 的 fiber：

```ts
import { FiberState, type Context } from '@deepseek-ai/cordis'

for (const runtime of ctx.registry.values()) {
  for (const fiber of runtime.fibers) {
    if (fiber.state === FiberState.PENDING) {
      console.log(`${fiber.name} is PENDING — a required service is missing`)
    }
  }
}
```

模块解析失败（路径/包名拼错）只经 logger 报告、不崩进程，且启动早期可能丢失——新增行毫无反应时先查拼写。

## 依赖驱动的加载

声明了 `inject` 的插件等待所有必需服务就绪才加载。运行期间依赖消失（提供方被替换/卸载）→ 插件自动 dispose（ACTIVE → DISPOSED），服务恢复后自动重载——防止消费方握着已失效的服务。

## 自动清理机制

通过 `ctx` 做的任何注册，在插件卸载时自动撤销：

- `ctx.on(event, handler)` —— 事件监听
- `ctx.tools.register(tool)` / `ctx.llm.registerAdapter(...)` —— 各类注册表
- `ctx.effect(() => cleanup)` —— 自定义资源

disposer 按注册顺序的**逆序**启动；多个异步 disposer **并发**执行，不保证逐个完成。有顺序要求的清理放进同一个 `ctx.effect()` 返回的 disposer 里串行 await。

## 嵌套上下文与 dispose

`ctx.plugin(child)` 创建子 Fiber：继承父上下文但独立生命周期，随父插件一同 dispose；返回的 fiber 句柄可手动 `await fiber.dispose()`（保证：自身注册全部移除、子插件递归卸载、Promise 在所有异步清理完成后兑现）。

## HMR（热模块替换）

配置变更或源文件变化（dev 模式）时：卸载旧插件（清理所有注册）→ 加载新代码 → 执行新的 `apply`。因为注册自动清理，热替换不会保留旧实例的注册。客户端半边还有 harness 内置的 dsh-client-hmr 浏览器热替换（见 [打包与安装插件](../基础/打包与安装插件.md)）。
